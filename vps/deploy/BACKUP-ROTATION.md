# ZohurNews backup rotation v2

Local full snapshots include news.sqlite, research.sqlite and academic.sqlite if present. Two complete restore points are retained under `/opt/zohurnews/backups/snapshots/<UTC timestamp>`. Every member has compressed and restored SHA-256 hashes, byte counts, gzip CRC verification and a SQLite integrity-checked online snapshot. A generation becomes visible with manifest.json and READY only after all members succeed. The source databases are read through SQLite online backup; their files, news and research projects are never pruned.

Rotation runs only after a successful new generation and verifies both retained generations before removing older ones. A failed new snapshot preserves existing generations and removes only its temporary staging folder. Stale staging folders owned by this module are removed under the shared backup lock after six hours. A free-space check precedes copying, with a progress check to stop before disk exhaustion. Local status is written to state/local-backup-status.json. Local and encrypted-cloud operations share state/backup.lock so a local generation cannot be removed during upload.

One-time legacy migration verifies a new full snapshot by decompression and SQLite integrity, restores the newest complete legacy generation (all currently required databases), then retains two generations before removing dated legacy backup files and three explicit pre-change full-database copies. Code/configuration files in the historical source backup directories remain. The cleanup plan/result is logged in state/legacy-backup-cleanup.json. No path under data/ is removed.

Google Drive uses the existing encrypted rclone destination. Retention is the union of the newest snapshot for each of seven distinct days, four ISO weeks and three calendar months; overlapping buckets share a snapshot, so 14 is a maximum, not an obligatory number of copies. A new cloud snapshot is copied back, checksummed, restored and SQLite-verified before its READY marker is published. Only previously complete, manifest-valid remote generations outside the retained set are purged. If authorization, upload or restore fails, no cloud retention deletion occurs. Old schema-1 two-database and current three-database manifests remain accepted.

Server authorization is separate from ChatGPT's Drive connection. Configuration is root-only `/opt/zohurnews/private/rclone.conf`. If absent, no upload or remote deletion is claimed; run the existing `sudo python3 /opt/zohurnews/releases/research-v3/deploy/offsite/configure_drive.py` interactively in the owner's terminal. OAuth tokens and the encryption passphrase must never be pasted into chat. Keep the recovery passphrase in a password manager/offline recovery copy. The existing configuration helper starts and restore-tests the first upload and enables the daily cloud timer only on success.

Tests: local rotation preserves original files, a corrupt retained snapshot prevents pruning, failed snapshot staging is cleaned up, legacy deletion requires two verified restore points, unknown source files remain, retention buckets cross calendar years and invalid manifests/CRC corruption are rejected. `python3 -m unittest discover -s deploy -p 'test_*rotation.py'`, `python3 -m unittest discover -s deploy -p 'test_backup_core.py'`, `python3 -m unittest discover -s deploy/offsite -p 'test_cloud_backup.py'`.
